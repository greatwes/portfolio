A little context.

I didn't start out building payment reconciliation systems or AI recruiting pipelines. Most of my work starts the same way: someone on a team is stuck doing something by hand that shouldn't need a person at all. A spreadsheet standing in for a database. A biometric terminal with no way to talk to the rest of the company's systems. A hiring process that depends on someone reading every resume one at a time.

I find that gap and build something that closes it properly: tested, resistant to being run twice by accident, and honest in the README about what it still can't do.

Most of what I build runs quietly for teams that will never read the code, which is kind of the point. The projects below are the ones I can actually show.

Systems, field operations

Biometric Attendance System

500+ staff clock in every day on a system that has no server for anyone to babysit.

A fingerprint terminal pushes every punch straight into a cloud warehouse, and a native Android app I built handles enrollment and admin on-site. Every write is idempotent, so a terminal that retries a batch can never double-count attendance, and a live dashboard reads from the same numbers the device just sent. I closed two SQL-injection surfaces in the write path and built a second sync layer so someone enrolled on one terminal can check in on any other, with no laptop or local server anywhere in the chain.

How I work.

Making unreliable things reliable

Retries, idempotency, dead-letter handling. Things that can run twice without causing twice the damage.

Designing for the failure, not just the happy path

Every integration I build gets asked "what happens when this is down" before it gets asked "does this work."

Testing without touching real infrastructure

If a test needs a live database or a live API to pass, it isn't a test I trust. Stub it, prove the logic, then verify for real once.

Handing off something a non-engineer can run

A system nobody but me can operate isn't finished. Documentation and a working README are part of the build, not an afterthought.

Got a process that needs fixing?

If it's held together by someone's memory and a spreadsheet, I'd like to hear about it. I usually reply within a day.
